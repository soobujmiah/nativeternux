# Ternuxx-owned Debian PRoot sessions

**Status (2026-10-20):** fixed profile inventory, exact-session ownership controls, foreground TTY login path, bounded health reads, and safe stale-record reconciliation are implemented. The dedicated `tx pgui` desktop lifecycle is now live-qualified for standalone `:0` and nested Xephyr `:2` inside Native `:1`; it uses a separate tracked supervisor, the existing Zink/Turnip handoff, and authenticated Native PulseAudio. The foreground PTY relay now has fixture coverage for input/output, SIGWINCH sizing, exit status, and terminal/fd cleanup; the Native CLI attached-login path has two recorded successful PTY verifications and exits (2026-10-19 and 2026-10-20), alongside multiple failed starts; the current-worktree TUI route passes focused tests but is not live-qualified. General profile-session attach/detach, arbitrary session stop, guest service management, and PRoot boot launch remain unqualified.

## Rootfs and legacy integration

The current Native Termux proot-distro installation discovers the Debian guest at $PREFIX/var/lib/proot-distro/containers/debian/rootfs. Discovery checks the absolute configured path, rejects a symlinked rootfs or launcher, and records device/inode identity. It does not modify the rootfs.

For isolated terminal qualification, the Native broker can explicitly select a separate `ternuxx-replay-NAME` container through `--guest-alias`. Session discovery/preflight, plan binding and the actual interactive launcher use the selected container. Default CLI profiles remain on `debian`; terminal clients cannot change the broker's selection. See [separate guest qualification](INTERACTIVE-PROOT-TERMINALS.md#separate-guest-qualification). A selected missing/unsafe guest fails instead of falling back to `debian`.

On the reviewed owner device, the db and droot shell aliases delegate to tx db --user sbj and tx db --root; see the [2026-10-23 alias migration evidence](../evidence/2026-10-23-native-legacy-alias-migration.md). Other installations may define different aliases, and tx db is the product command. tx db performs an immediate normal proot-distro login with validated account, display, audio, and backend settings; it is not a broker-tracked session. A normal login invokes the installed proot-distro hook, which may write the guest /etc/profile.d/termux-profile.sh and container sidecar state. tx db does not preview or roll back that package-owned hook effect. The debian-interactive broker profile resolves the one ordinary guest account from the selected rootfs `/etc/passwd`; it does not embed an owner-specific username. The exact account is returned in preview, included in the plan identity, rechecked before start, and used by the launcher. Ambiguous accounts make the profile unavailable rather than choosing one. It runs /usr/bin/env TERNUXX_PROOT_SESSION=<random-id> /bin/bash --login as the explicit guest command on a private controlling PTY. It requires a real caller terminal, relays terminal input/output and size changes, supports shell job control, and remains attached until the guest shell/session exits. Exit status is persisted in schema v3. It does not create a detached terminal multiplexer, start a GUI or service, or alter Termux:Boot. The tx mng proot start preview also discloses that package-owned side effect; it does not snapshot or roll it back. Its default guest working directory is left to proot-distro/Debian login behavior.

isolated-probe remains a bounded headless session using proot-distro login --minimal debian and a fixed /bin/sleep target. It redirects stdio to /dev/null; it is a diagnostic profile, not a workstation.

## Ownership and persistence

The private registry at $TERNUXX_STATE_DIR/proot/sessions.json is version 3, mode 0600, and atomically replaced under an OS file lock. Version 1 and 2 records are read and upgraded in memory, then written as version 3 on the next mutation. A record holds a stable session ID, profile/version/mode, rootfs and launcher device/inode identity, a random marker, expected fixed argv, PID, kernel process-start ticks, session/process-group identity, timestamps and bounded transition history. It stores no shell environment values or secrets.

Read-only session inventory reads one complete old-or-new registry snapshot without creating the lock file. Writers publish with atomic replacement, so listing does not need a lock or leave state behind.

A live session is considered Ternuxx-owned only when PID and process-start identity match, PID is the recorded session/process-group leader, the private marker is visible, the profile signature matches the actual translated proot argv and (for the interactive profile) the kernel-resolved cwd directory identity matches the rootfs and numeric guest identity matches the passwd entry, and the rootfs/launcher inode identities still match. Cwd comparison uses device/inode identity because procfs may display the rootfs cwd as `/` inside a PRoot namespace even when it is the same directory. proot-distro rewrites public distro/user arguments, so verification uses the actual proot command, guest rootfs cwd, passwd UID/GID, fixed login argv and random marker rather than searching for the removed public --user/debian tokens. The marker is passed as a guest env argument because proot-distro does not preserve the host marker in the resulting PRoot process environment. PID, command text, process group, or rootfs identity alone is insufficient.

Unmanaged PRoot sessions are only reported by the read-only inventory and are never adopted. A persisted running record with no matching process is presented as unverified while retaining its recorded_state; reads do not rewrite or delete it. Stop uses a fresh preview plan, revalidates process identity and filesystem identities immediately before signaling, and sends SIGTERM to the exact owned headless probe group. Interactive close uses SIGHUP for the owned terminal leader and its verified job-control groups within the same private kernel session; each child-group representative is rechecked for process-start, session and group identity before signaling. The stop plan binds profile/signal semantics and discloses the scope. A changed or unverified group is skipped, and remaining processes produce `stopping` without escalation. It waits boundedly and never sends a force signal. If identity is unclear, it refuses.

A graceful stop timeout retains a readable `stopping` record for subsequent inspection/retry. Interactive shells ignore SIGTERM and job control may give them a different process group from the tracer; the [fresh replay](../evidence/2026-10-22-fresh-setup-and-probe-safety.md) reproduced and fixed both close defects. A crash after starting a child can leave an unverified registry entry. tx mng proot recover SESSION_ID is read-only. tx mng proot reconcile SESSION_ID previews an explicit registry update; applying its exact plan marks the old record stopped only when /proc proves the PID absent, replaced, or exited. It never signals the current PID, adopts a process, or removes the audit record. Live-but-unverified records remain untouched. A completed interactive shell is marked stopped by its supervising tx command when it returns. If the parent is killed unexpectedly, the process is not automatically reclaimed.

## Supported interface

- tx mng proot profiles list|show
- tx mng proot sessions list|show|health SESSION_ID
- tx mng proot start --profile ID prints a plan by default.
- Repeat with --yes --plan-id ID to apply the selected plan.
- tx mng proot stop SESSION_ID prints a plan; repeat with --yes --plan-id ID to stop only that session.
- tx mng proot reconcile SESSION_ID previews safe exit reconciliation; apply only with --yes --plan-id ID.

Profiles are fixed and typed; user-supplied shell strings are not accepted. The isolated probe and interactive login build launch environments without any LD_* variables, preventing inherited host loader overrides from reaching the native launcher or guest. The current `debian-interactive` profile is a synchronous foreground terminal login whose PTY master belongs to the caller; reattach and shared cross-client streaming are not implemented. The general Web profile-session API retains its fixed probe/owned-stop scope. A separate Native terminal broker now provides CLI/TUI/Web/xterm.js/GTK/VTE terminal paths under its own typed session/attachment contract; one disposable guest cross-client lifecycle is recorded as passed; broad lifecycle repeatability and full client mutation parity remain open. GTK therefore has a terminal widget, while the older direct foreground profile API remains synchronous. The owner now requires interactive terminal support in CLI, TUI, Web, and GTK. See [shared interactive PRoot terminal design](INTERACTIVE-PROOT-TERMINALS.md) for the broker architecture, security model and current P4 qualification boundaries. No arbitrary guest command API or Web/GTK host shell is supported.

The file mtime observed after our attempts predated them, but no before-hash exists; attribution cannot be established, so no further live login or rootfs operation was attempted during the 2026-10-21 audit. ## Native-owned workstation handoff (2026-10-20)

Ternuxx Native Termux is the authority for its host display/audio lifecycle and Debian handoff. Default guest identity resolution reads the installed Debian rootfs etc/passwd and accepts one ordinary non-root account with home /home/NAME; no Ternux executable or state file is required. Ambiguous accounts require an explicit --user.

For Native tx db, managed interactive PRoot sessions, app launch, and bounded verification, Ternuxx passes the active DISPLAY (default :1), Debian Zink/Turnip variables, and a validated Native PulseAudio cookie through one bind to /tmp/.ternuxx-pulse-cookie. Zink passes /dev/kgsl-3d0 as /dev/kgsl and the available /dev/dri tree. These are host capabilities with guest ABI-compatible Mesa userspace; Native Bionic libraries are never copied into Debian. VirGL remains an optional route, not the active default. CPU remains the baseline. NPU is experimental and unqualified.

The installed proot-distro login implementation writes /etc/profile.d/termux-profile.sh from the environment supplied to each normal guest login. This is its login-shell persistence mechanism, not a Ternux CLI dependency. Leave that package-generated file and its writer intact. Ternuxx writes the same Zink/display/audio baseline for each Debian login and applies selected backend variables after the shared profile has loaded, to the launched process only. Thus a VirGL shell does not change what a parallel or later default Zink login inherits; a su - from that VirGL shell returns to the stable Zink baseline. Keep unrelated sudoers and guest profile hooks untouched. A separate explicit Ternux session adapter remains optional; normal Ternuxx operation does not query it.


## Dedicated full Debian desktop (`tx pgui`)

`tx pgui` is the user-facing launcher for the existing Debian XFCE desktop. With Native GUI stopped, it supervises Termux:X11 `:0` and the Debian XFCE command as a Ternuxx-owned `provider=proot` desktop session. With Native GUI running on `:1`, auto mode launches a foreground Debian session inside Xephyr `:2`. Explicit modes are `tx pgui start --mode standalone` and `tx pgui start --mode nested`; `tx pgui status` reports both the managed standalone record and display occupancy, and `tx pgui stop` stops only the identity-verified standalone session. Close nested XFCE with Ctrl-C in the launching terminal.

Standalone `:0` and Native `:1` are mutually exclusive. Both lifecycles share the private desktop lock: nested mode holds it for its full lifetime, while standalone startup uses it to serialize startup and native lifecycle changes. Native start checks the standalone PRoot record and refuses an overlap. Nested uses the Native `:1` host display for Xephyr, then guest display `:2`; Debian applications keep their glibc Mesa/Zink/Turnip libraries. PulseAudio remains Native-owned at `tcp:127.0.0.1:4713` with the private cookie bound into the guest. Existing app shortcuts continue to launch individual Debian programs on Native `:1` through the shared management service.

The fresh Debian Trixie installer includes `xserver-xephyr`, `x11-utils`, and `mesa-utils` in its selected package manifest; the 2026-10-23 replay installed and verified its requested packages. This does not migrate or install packages into an already-existing Debian guest. See [the live GUI qualification](../evidence/2026-10-20-proot-full-gui.md) for tested renderer, audio, cleanup, and limitations, and [the fresh package replay](../evidence/2026-10-23-disposable-debian-replay.md) for package/setup evidence. Neither nested DRI3 nor nested GLX is qualified; GUI visual confirmation remains an owner check.
