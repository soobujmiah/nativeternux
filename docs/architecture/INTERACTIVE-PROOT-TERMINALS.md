# Shared interactive PRoot terminal design

**Status:** P4 architecture proposal. P3 is complete. No shared PTY broker or Web/GTK terminal transport is implemented. This optional provider feature must not be required for Ternuxx Native boot, SSH, CLI, management, or native workloads; those remain usable without PRoot.

**Implementation progress (2026-10-22):** `lib/terminal_broker.py` provides bounded length-prefixed JSON frames, duplicate-key rejection, a private Native Unix socket endpoint, Linux same-UID peer credentials, and a strict common terminal request envelope. Existing socket paths are never adopted or unlinked. Its in-memory attachment registry enforces one writer, broker-generation binding, per-request principal binding, bounded input and retained output, output sequence cursors, and detach without session termination. The typed dispatcher requires injected authorization, session-identity, PTY input/resize, and previewed close callbacks. A read-only broker-status operation is wired through the shared service for CLI/TUI/Web/GTK resource inspection. A fixture-tested `TerminalPTYRuntime` now owns an injected exact-preview PTY master and relays bounded input/output, resize, EOF, and broker-close state. The production socket endpoint is not wired to this runtime; no interactive client connects and the feature is not usable yet.

**Owner requirement:** interactive terminal support is required in CLI, TUI, Web, and GTK. The earlier CLI/TUI-only boundary proposal is withdrawn. Web and GTK must not gain a host shell, arbitrary argv/command interface, or bypass around Android app isolation. The owner confirmed on 2026-10-21 that P3 must be completed and confirmed before P4 begins. This stages the shared broker and all-client transports in P4; it does not waive the requirement. See the [owner phase-order decision](../evidence/2026-10-21-p3-before-p4-owner-decision.md).

## Existing architecture audit

- `lib/proot_sessions.py` already owns fixed profile discovery, exact preview plans, the private session registry/lock, guest rootfs and launcher identity, fixed login environment, process start-time/session/process-group checks, and exact-owned stop/recovery previews.
- `debian-interactive` uses `pty.fork()` and `_relay_interactive_pty()` to give one foreground CLI/TUI caller a controlling PTY. The caller owns the PTY master and performs stdin/stdout relay and `SIGWINCH` sizing. The master closes when that foreground command exits. Session health reports `reattach_supported: false`; the manager has no attach, detach, resize, input, output-stream, or per-attachment authorization operations.
- `lib/management_service.py` is the typed allowlisted control plane. It accepts only the trusted local CLI adapter and already has preview/start/list/health/stop/recovery operations for fixed profiles. It rejects extra fields and has no generic command operation.
- Web uses the loopback-only `management_http_server.py` and `management_http_adapter.py`. Existing Web sessions provide bearer authentication, explicit scopes, CSRF checks, durable idempotency for mutations, and origin checks. Web `proot.start` is intentionally restricted to the fixed 300-second `isolated-probe`. The HTTP server is a bounded request/response server; it has no terminal byte-stream protocol or WebSocket implementation.
- GTK calls the typed service through `scripts/management_desktop_bridge.py`. Its PRoot session controls are discrete list/preview/apply/recovery operations. The GTK app has no terminal widget or long-lived PTY bridge; its `GtkTextView` is a detail display, not a terminal emulator.
- TUI and CLI already run inside a local terminal, but their current attached relay is process-bound. The TUI route has fixture evidence only. Live guest login qualification remains a separate P4 gate; no guest should be entered during this P3 architecture work.

## Proposed shared design

Use one Ternuxx-owned native PTY broker as the sole PTY/session owner, while retaining the existing typed management service as the authorization and operation boundary. All four clients become adapters to the same broker and session registry; they do not spawn their own PRoot command or hold independent PTY masters.

### Broker and session identity

- Run the broker as the native Termux user under a Ternuxx-owned service supervisor. Keep its control endpoint on a private `AF_UNIX` socket below the mode-0700 Ternuxx state directory, with a mode-0600 socket and no TCP listener.
- Validate socket parent ownership/mode, reject symlinks, and check Linux peer credentials (`SO_PEERCRED`) against the expected Termux UID for every local connection. Do not use root, Shizuku, ADB, or Android permission changes.
- Reuse `proot_sessions` records, registry locking, plan binding, discovery fingerprints, and exact process identity. Extend the record with broker generation, PTY attachment state, monotonically increasing output sequence, and the active attachment owner. Store only hashes of any short-lived channel grants; never store terminal bytes or passwords.
- Create only the reviewed `debian-interactive` profile with its fixed guest user, fixed login argv, rootfs/launcher identity, and environment builder. The broker must reject caller-supplied command, argv, rootfs, user, environment, or working-directory overrides. No host shell is an available profile.
- Permit one writable attachment per session in the first implementation. Bind every action to an exact Ternuxx session ID, broker generation, client attachment ID, and authorization context. Reject stale IDs, reused tickets, duplicate writers, and cross-session requests.

### Shared lifecycle and failure handling

- Keep `proot.start.preview` / `proot.start` as the only session creation path, with the existing exact plan ID and explicit confirmation. New `attach`, `detach`, `input`, `resize`, `output`, and `close` calls must be typed, narrowly allowlisted operations, not a generic RPC or shell endpoint.
- Detach means release the client channel only; it does not signal the guest. Explicit close uses the existing fresh ownership revalidation and exact-session preview/confirmation before a bounded `SIGTERM`. Never use `SIGKILL` or adopt a pre-existing Ternux/PRoot process.
- Bound input frames, dimensions, output chunks, retained output, idle time, and concurrent sessions. Apply backpressure; reject invalid UTF-8 only where the selected protocol requires text, otherwise preserve terminal bytes. Do not persist terminal output or put it in logs.
- If the broker or client dies, mark attachment state disconnected and reconcile the recorded PID/start ticks, process group, rootfs identity, and broker generation. A broker restart must not adopt a live process or claim that the PTY can be reattached. Uncertain records stay `unknown`; only an exact verified stop plan can signal a process.
- A broker crash closes the master PTY. Session survival and recovery behavior must be proven with a disposable guest before enabling detach/reattach claims.

### Client adapters and authorization

- **CLI:** use the broker over the private Unix socket; preserve normal terminal raw-mode restoration, `SIGWINCH`, Ctrl-C/EOF behavior, exact preview confirmation, and clear detach versus close choices.
- **TUI:** use the same client library and operation contract. Its interactive terminal view remains attached to the TUI's controlling terminal; selecting a session never bypasses broker ownership checks.
- **Web:** keep the listener bound to `127.0.0.1` and use the existing `proot.session.manage` scope, CSRF, exact Origin, and management-session lifetime. Create a short-lived, single-use channel ticket through an authenticated CSRF-protected request; bind it to the authenticated Web session, exact PRoot session ID, and exact Origin. Do not put bearer tokens or tickets in URLs. A separately reviewed streaming transport must validate each channel before any bytes flow; it may not start from a guest command string. Use a maintained terminal renderer and record its provenance before shipping.
- **GTK:** use the same broker client and typed session operations. Embed a maintained GTK terminal widget only after its Termux package/build provenance and version are verified. The existing detail `GtkTextView` must not be repurposed as a terminal or a shell-output sink.
- Revoking a Web management session invalidates its channel tickets and active Web attachment. Client authorization is checked at attach and again for session-changing operations; ordinary terminal input is limited to the one attached writer for that exact authorized session.

## Why this is not safe to finish in P3

P3 defines and fixture-verifies ownership contracts; the roadmap explicitly reserves PRoot session implementation and live guest qualification for P4. The current PTY master is tied to one foreground CLI/TUI process, there is no broker or reattach protocol, the Web transport has no terminal streaming endpoint, and the GTK client has no terminal widget. Implementing all four clients now would require a new service lifecycle, session protocol, Web streaming/auth handshake, GTK terminal dependency, and disposable guest/device integration work. The current guest's login hook can write guest-owned profile state, and live interactive login is not yet qualified. No safe P3-only patch can meet the owner's all-client requirement without claiming unsupported behavior or testing against the protected existing guest.

## Phased implementation and acceptance

1. **P3 contract (complete):** record this owner requirement, reuse boundaries, auth/session model, failure behavior, and negative tests that prove Web/GTK cannot escape the existing fixed-profile allowlist. P3 is recorded complete before this optional P4 integration work.
2. **P4a broker core:** implement the local Unix-socket broker, fixed-profile spawn, session ownership/attachment schema, bounded PTY protocol, serialized lifecycle, and crash reconciliation. Test with a fake launcher and disposable rootfs fixture; prove socket permissions, peer UID checks, exact session binding, stale-plan rejection, duplicate-writer rejection, bounded I/O, and no arbitrary argv/environment.
3. **P4b local clients:** migrate CLI and TUI to the broker; add GTK terminal-widget dependency and client; verify attach/detach/resize, terminal restoration, close semantics, and client exit behavior with isolated fixtures and a disposable guest.
4. **P4c Web client:** implement a separately reviewed loopback streaming transport with one-use session-bound tickets, Origin/auth/CSRF checks, revocation, backpressure, and a maintained terminal renderer. Test missing/expired/replayed tickets, wrong origins, revoked sessions, cross-session IDs, oversized frames, and disconnected clients. Do not add another network bind or broad Web capability.
5. **P4d device acceptance:** only after the disposable guest and rollback gates pass, request an explicit maintenance window for one exact existing-Debian login. Verify the fixed account/rootfs, all four client attaches, session isolation, explicit close, preserved legacy `tx db` behavior, and post-failure reconciliation. Never reboot as part of this PRoot work.

This document records the owner-required all-client contract; it does not implement the broker or qualify P4 guest behavior. P3 completion still requires its independent exit gates, including Native cold-boot verification in an owner-approved device window. Until then, the all-client terminal capability remains planned and unavailable in Web/GTK.

**2026-10-22 continuation:** `proot_sessions.spawn_login_interactive()` now separates exact-preview fixed-profile PTY startup from the caller-owned foreground relay. It retains rootfs/launcher identity checks, private session/group checks, and verified failure cleanup, then returns the master FD only after session ownership is verified. The existing CLI/TUI path still performs its foreground relay through this helper. A fixture mocks `pty.fork`, process identity, and verification and confirms the helper does not require a client TTY. The helper is not connected to a persistent broker loop: no endpoint spawns or relays a PTY, and no terminal client can attach. This is still not a usable broker terminal feature.

## Legacy Ternux CLI retirement

On 2026-10-22, the old Native Ternux command and Debian guest companion were retired only after the current Ternuxx CLI and fixed guest verifier were exercised. Both retirements require an exact preview and move the named target into a private same-filesystem backup without signaling PRoot. The guest companion and host CLI each have an explicit rollback command recorded in the [runtime and legacy CLI follow-up](../evidence/2026-10-22-p4-legacy-cli-and-runtime-recheck.md). A separate prior-name recovery compatibility alias remained at that checkpoint.


**2026-10-22 runtime fixture continuation:** `TerminalPTYRuntime` now binds an exact preview to one injected `spawn_login` result, verifies the fixed interactive profile identity before exposing a writer attachment, retains one PTY master, relays bounded input/output and resize, and marks the Ternuxx session unknown on broker shutdown without signaling it. EOF/shutdown releases the broker generation's writer lease once. Fixture coverage passes 10/10. This runtime is not constructed by a service entrypoint; the Unix endpoint still serves only its existing dispatcher, so start/attach/input/output/resize/detach/close are not available to CLI, TUI, Web, or GTK.
