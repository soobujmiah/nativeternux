# PRoot GUI apps on native X11 sessions

## Separate Native PRoot Apps menu

Ternuxx scans the installed Debian rootfs application directory (`/usr/share/applications`) and generates a **PRoot Apps** category in the Native XFCE menu. Native desktop startup runs this sync automatically. After installing or removing guest GUI apps while Native XFCE stays open, refresh with:

```sh
./tx mng papps sync
```

The sync includes visible GUI application entries, skips hidden, terminal-only, malformed, and session-logout entries, and preserves conflicting files that it does not own. Generated entries route by Debian desktop-entry ID through `proot.app.launch`; the service expands documented desktop field codes into an argument vector and starts the guest command directly without a shell. The menu overlay is stored in Ternuxx's private Native XFCE XDG paths, merges the system menu, assigns generated launchers only to the custom PRoot category, excludes them from generic Accessories and Accessibility menus, and groups them under **PRoot Apps**. The parent-merge behavior follows the [freedesktop Desktop Menu Specification](https://specifications.freedesktop.org/menu/latest-single/).

A single menu entry can also be launched from Native Termux:

```sh
./tx mng app launch --desktop-id thunar.desktop --display :1
```


The supported single-app path runs an individual GUI application from the installed Debian PRoot as a window on an already-running native X11 session. The default target is Ternuxx. An explicit Ternux target is available when the owner has already started the Native Termux/Ternux desktop; it requires a selected display and read-only Ternux status/backend checks. Neither target is started or stopped by this app handoff.

```sh
# Opens Debian's XFCE Terminal in the current native desktop
xgo

# Or start a chosen PRoot GUI application
xgo thunar
xgo xmessage 'Hello from Debian PRoot'
```

The current `~/x.sh` is a short compatibility wrapper to the checked-in `scripts/proot-x11-app.sh`; the current `x` and `xgo` shell aliases invoke it. The helper requires an already-running Ternuxx Native display, verifies guest X11 connectivity, starts or reuses the Ternuxx Native audio service, and launches one validated guest command. It does not invoke the separate Ternux CLI, start an Android Activity, or stop either desktop. `killx` currently prints a window-close hint and does not signal processes. These are live host observations recorded in [entrypoint inventory evidence](evidence/2026-10-22-legacy-entrypoint-inventory.md); shell config was not changed.

The shared management service provides the provider-aware catalog and operations:

```sh
./tx mng shortcuts list
./tx mng shortcuts plan add files
./tx mng shortcuts apply add files --plan-id PLAN_ID --yes
./tx mng app launch files
# Explicitly launch a Debian app on the already-running Native Termux/Ternux :1 session
./tx mng app launch files --display :1
```

The add/remove helper asks for confirmation after showing the exact target. The X11 shortcut manager uses the same service and displays a confirmation dialog before menu changes. The older fixed shortcut catalog remains available for preview/apply management; automatically discovered menu entries use the guest desktop-entry ID through the same shared service. Removing a launcher never closes a running app or stops X11/XFCE. Existing user-edited or unrecognized launchers are reported as conflicts and left untouched; exact legacy entries generated by the previous helper can be updated safely after confirmation. The current `xgo` alias remains a convenience entrypoint to the Ternuxx single-app helper, but it is not a required compatibility contract. `tx db` is the canonical managed Debian shell path; bare `db` and `droot` aliases currently call `proot-distro` directly and can bypass its provider handoff.

The owner’s current Native shell defines `db` and `droot` as direct Debian login aliases. The current `x` and `xgo` aliases call `~/x.sh`, which delegates to the checked-in Ternuxx X11 app helper. No legacy-backup path is asserted by this current-state note; exact backups must be verified before any future alias migration. `tx db` remains the canonical Ternuxx command.

This opens PRoot applications as individual windows in the selected existing desktop; it does not create a second full XFCE desktop. On 2026-10-18 the owner visually confirmed the PRoot `xmessage` window on native display `:1`. This proves an individual PRoot X11 client can render there. The owner later confirmed the Thunar window was also visible; a full second XFCE desktop remains unverified. A nested full desktop would need a nested X server such as Xephyr, which is not installed in the inspected guest. Installing additional Debian packages remains preview-first and is not part of this workflow.

The Android dual-app Termux:X11 profile (user 999) is deferred. Its Activity did not show the PRoot GUI in the owner test; the native shell also cannot control or inspect that profile across Android users. See the historical [display 0 experiment](PROOT-GUI-DISPLAY0.md).

## Full PRoot desktop policy — native :1 only

The supported target is the existing native Termux:X11/XFCE desktop on `:1`. A selected Debian GUI application can open as a window there through the shared `management app launch` operation. Starting a second Termux:X11 Activity or a separate PRoot display `:0` is not the target experience.

A full Debian XFCE session must run inside a nested X server window hosted by `:1`; starting another `xfce4-session` directly on `:1` risks competing with the native window manager. The checked Debian guest currently has `startxfce4` and `xfce4-session`, but no `Xephyr` or `Xnest`. Therefore new `:0` PRoot GUI starts are disabled until the nested adapter and its exact guest dependency plan are implemented and qualified. The legacy script retains read-only status and ownership-checked stop for any prior `:0` session. No Debian package or rootfs change is made by this policy.

## Independent Ternuxx guest lifecycle status (2026-10-19)

`tx proot status` is an installed-distribution inventory, not a claim that the Debian guest belongs to Ternuxx. The current Native Termux inventory reports Debian installed with ownership unverified. A read-only `proot-distro list` confirms the same Debian container path under `$PREFIX/var/lib/proot-distro/containers/debian/rootfs`. `tx proot gui start` remains disabled. The named-app integration uses `proot-distro login`; it does not provide a Ternuxx-owned persistent guest supervisor or safe guest stop/restart contract.

A recorded Ternuxx `:0` session file reported `running`, but its supervisor, X11, and desktop PIDs were absent at inspection. The record was preserved. Do not infer that the guest is stopped solely from this record or remove its X11 artifacts. Until process-group membership, rootfs sharing, display ownership, and state migration are covered by an adapter, full independent guest lifecycle and concurrent legacy/Ternuxx sessions remain unsupported/unverified.

## Ternuxx-owned session probe (2026-10-19)

A private version-1 PRoot session registry and ownership checker are available in
lib/proot_sessions.py. The only executable profile in this increment is
isolated-probe: proot-distro login --minimal debian -- /bin/sleep N. PRoot-Distro
documents --minimal as an isolated mode with only /dev, /proc and /sys mounted;
it does not bind the Termux home, /tmp, or X11. Rootfs and launcher device/inode,
session ID, process PID/start-time, environment marker, and newly created session
and process-group identity are recorded. Stop requires an exact preview plan,
confirmation and revalidation; it sends only SIGTERM to the process group created
for that exact session and never escalates to SIGKILL.

A disposable isolated-probe session was started and stopped against the existing
Debian rootfs. This proves the constrained probe lifecycle, not interactive guest
entry, workstation startup, graphics, or general-purpose PRoot lifecycle. Existing
unmanaged sessions remain inspection-only. The active Codex session and floating
X11 GUI were not changed.


## Native Ternuxx default (current)

Current Ternuxx app launches always attach to the verified Native Ternuxx display. The CLI, shared API, TUI, and helper do not invoke the separate Ternux CLI or select its session. The dated Ternux handoff described below remains historical evidence only; a clean Ternuxx setup does not depend on that repository.


## Shortcut click-path follow-up — 2026-10-20

The previous Native menu used `tx app -- PROGRAM`, but the checked-in CLI did not register the `app` command, so clicking those entries could not reach the shared app launcher. The compatibility route is now allowlisted and the generated menu uses the typed `mng app launch --desktop-id ID` service operation. Live tests ran the generated Thunar entry through `gtk-launch` and through the shared CLI route on Native `:1`; `xdotool` observed a visible `sbj - Thunar` window. Agent-side menu clicking was not performed. Runtime category XML and generated desktop entries were validated; visual confirmation of the category label remains for the owner.
