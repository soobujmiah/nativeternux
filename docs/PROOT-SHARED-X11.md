# PRoot GUI apps on native X11 sessions

The supported single-app path runs an individual GUI application from the installed Debian PRoot as a window on an already-running native X11 session. The default target is Ternuxx. An explicit Ternux target is available when the owner has already started the Native Termux/Ternux desktop; it requires a selected display and read-only Ternux status/backend checks. Neither target is started or stopped by this app handoff.

```sh
# Opens Debian's XFCE Terminal in the current native desktop
xgo

# Or start a chosen PRoot GUI application
xgo thunar
xgo xmessage 'Hello from Debian PRoot'
```

The current `~/x.sh` is owner-customized and intentionally left untouched; it delegates to the Ternuxx single-app helper. The Ternuxx default reads its own active display. The explicit Ternux target checks `ternux status --json`, the configured Zink/Vulkan backend, the selected X11 socket, and Debian guest X11 connectivity before launching the fixed catalog application. It does not call Ternux start/stop, request an Android Activity, or claim X11/audio lifecycle ownership. Close the individual PRoot application's window to end that app. The current `killx` alias is warning-only and remains untouched.

The shared management service provides the provider-aware catalog and operations:

```sh
./ternuxx management shortcuts list
./ternuxx management shortcuts plan add files
./ternuxx management shortcuts apply add files --plan-id PLAN_ID --yes
./ternuxx management app launch files
# Explicitly launch a Debian app on the already-running Native Termux/Ternux :1 session
./ternuxx management app launch files --session ternux --display :1
```

The add/remove helper asks for confirmation after showing the exact target. The X11 shortcut manager uses the same service and displays a confirmation dialog before menu changes. Generated desktop entries call `management app launch`, which dispatches only catalog IDs. Removing a launcher never closes a running app or stops X11/XFCE. Existing user-edited or unrecognized launchers are reported as conflicts and left untouched; exact legacy entries generated by the previous helper can be updated safely after confirmation. The older `xgo` path remains available as an advanced CLI compatibility launcher.

`db` and `droot` remain the existing Debian shell-entry aliases. The old `x.sh` and GUI alias definitions are backed up with mode 0600 under `~/.local/share/ternuxx/legacy-backups/2026-10-18/`.

This opens PRoot applications as individual windows in the selected existing desktop; it does not create a second full XFCE desktop. On 2026-10-18 the owner visually confirmed the PRoot `xmessage` window on native display `:1`. This proves an individual PRoot X11 client can render there. The owner later confirmed the Thunar window was also visible; a full second XFCE desktop remains unverified. A nested full desktop would need a nested X server such as Xephyr, which is not installed in the inspected guest. Installing additional Debian packages remains preview-first and is not part of this workflow.

The Android dual-app Termux:X11 profile (user 999) is deferred. Its Activity did not show the PRoot GUI in the owner test; the native shell also cannot control or inspect that profile across Android users. See the historical [display 0 experiment](PROOT-GUI-DISPLAY0.md).

## Device check — 2026-10-18

The owner confirmed the PRoot `xmessage` probe appeared on native `:1`. A later PRoot Thunar launch was visually confirmed by the owner while native supervisor, X11, and XFCE remained running. The menu manager has since been moved to the shared management service. Its read-only inventory preserves customized/unrecognized existing entries as conflicts; no launcher was changed during this repository verification.


## Current explicit Ternux handoff — 2026-10-18

The live Native Termux host reported Ternux v1.4.0 `running`, X11 `yes`, backend `zink`, Vulkan `yes`; the renderer summary field remained `unknown`. In the existing Debian 13 guest, `DISPLAY=:1 glxinfo -B` reported Mesa Zink Vulkan 1.4 on Adreno 825 (`MESA_TURNIP`) and `Accelerated: yes`. `./ternuxx management app launch files --session ternux --display :1` started Debian Thunar on that existing display; the process remained active after launch and was deliberately left open. This proves the selected guest client starts against `:1`; it does not prove GUI visibility via machine observation, Ternux display ownership, full desktop lifecycle, or a performance benchmark. No Ternux/Ternuxx start/stop, Activity request, PRoot session close, or `x.sh`/`killx` edit occurred. Detailed evidence: [2026-10-18 Ternux session app handoff](evidence/2026-10-18-ternux-session-app-handoff.md).
